# Form-centric extension status

The built extension uses a small popup and inline controls. The worker stores the selected category and captured page context in Chrome session storage, reinjects the field adapter after ordinary navigation and SPA history changes, and carries a session into a tab opened by the current tab. Stopping removes that tab's session. The Options page holds saved-answer and provider configuration.

The scanner handles text inputs, textareas, native selects, radio/checkbox groups, accessible ARIA comboboxes and file inputs. Nearby visible question text takes precedence over array-style HTML names. The inline **Saved answers** control can search by label or wording. Selecting an answer inserts it and adds the observed question as an alias to the same companion record. The host reindexes that template's existing semantic vector. Exact user-approved mappings fill blank fields automatically on subsequent visits. Editing label or wording stays on the same template ID, while subsequent changes to a mapped form field save automatically. A new alternative answer requires the explicit **Create another answer** action. AI help appears only for free-form text controls. File inputs offer an explicit picker and attach the selected file to the page input, without retaining the file or submitting the form. Explicit inline generation uses existing `prepare_form`, `generate_initial`, `render` and `record_feedback` events. Captured page context is sent only after the user chooses the popup context action and explicitly requests generation.

## Remaining acceptance gaps

- The companion returns `autofillEligible: false` for search and declares `capabilities.autofill: false`. Semantic top-k matches cannot safely drive unattended insertion. Only explicit question-to-template mappings created by the user are automatically filled; semantic autofill needs a supported context-aware unique-match decision.
- The companion now exposes narrow `template_get` and `template_update` operations for stable-ID editing and alias reindexing; the agent event schema remains unchanged. Existing 0.1.0 companion installations must be upgraded to 0.1.1 before these controls work.
- Files can be selected and attached to a form input during the current page interaction. Persistent automatic attachment from a local disk path would require an explicit file-selection/storage design and careful handling of Chrome's native-messaging size limits; it is not implemented.
- ARIA-compliant comboboxes and option lists are supported. Arbitrary framework widgets without accessible roles/options still need site-specific adapters; the Colorado control and the reported real 17-field site were not provided for direct regression testing.
- The previous installed companion and extension were not exercised together in a disposable Chrome profile for this change. Unit tests and the production bundle verify pieces, not the full user journey. No live provider request was made.

Build from `interface/` with `npm.cmd run build`, `npm.cmd test`, and `npm.cmd run package:store` on Windows. This makes `dist/` and `artifacts/questionnaire-extension-0.1.1.zip`. Build the 0.1.1 companion with `packaging/build-windows.ps1`; see `windows-release.md`. Unpack the ZIP directly into the stable `QuestionnaireAssistantExtension` folder under the AnswerCache project, then reload that unpacked extension in `chrome://extensions`. Keep the path stable so its unpacked ID and installer registration continue to match.
